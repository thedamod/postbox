# Production Email Client Notes

## Mobile and server

The mobile app should not become the IMAP server. Long-lived IMAP connections,
OAuth refresh tokens, mailbox polling, retry queues, and push delivery need a
durable process that can run when the phone is offline. A phone-hosted server
would be suspended by iOS and Android, lose inbound connections on network
changes, and expose provider credentials to the device.

The production shape is:

- A central sync worker owns provider connections and durable sync jobs.
- The API exposes a cursor-based mailbox projection for web and mobile.
- Mobile keeps a local SQLite projection for offline reads and an outbox for
  actions such as read, star, archive, and send.
- Mobile reconciles on foreground/resume and through OS background tasks when
  available.
- The server sends push notifications for new-mail events. The device stores
  only its push token and account/session credentials, not the provider's
  refresh token where avoidable.

This repository already has the provider-agnostic sync engine, SQLite storage,
UID/UIDVALIDITY cursors, a shared API, and mobile foreground reconciliation.
The next production additions are a durable queue (for example Postgres plus
a queue worker), an events/outbox table, push-token registration, and Expo
background task/notification adapters.

## Sync requirements

- Keep one sync cursor per account and folder.
- Treat UIDVALIDITY changes as a mailbox reset and rescan the folder.
- Fetch envelopes and flags first; download RFC822 bodies only for unknown
  messages.
- Make sync idempotent by provider UID plus Message-ID where available.
- Coalesce concurrent syncs for the same account and folder.
- Persist job state outside process memory before running multiple server
  instances.
- Expose retry state and the last successful cursor to clients instead of
  making the UI wait on a long request.

## Search requirements

FTS5 is appropriate for a local SQLite projection when its index is maintained
transactionally. Search should use safe prefix terms while typing, support
field filters, return stable relevance ordering, and hydrate only the rows
needed for the list. Full message bodies should not be loaded for every search
hit. A larger deployment can move this same query contract to PostgreSQL FTS
or OpenSearch without changing the UI.

## Notifications

Notifications should be event-driven from the sync worker, not generated by a
mobile polling loop. The worker emits a new-message event after the message is
committed, deduplicated by account and provider Message-ID. A notification
service then sends the push and records delivery attempts. This prevents a
crashed UI, duplicate sync, or retry from producing duplicate notifications.
